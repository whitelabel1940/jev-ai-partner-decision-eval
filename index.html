AIパートナーの判断層としてDecision Modelは使えるか

Jev 1.13.0と4つの汎用モデルによるholdout評価

位置づけ

本稿は、一般向けに簡略化する前の技術原本である。
評価の経緯、途中で棄却・修正した仮説、仕様監査、感度分析、deployment simulationまで含めて記録する。

Jev公開後の関連研究については、本評価の設計・実行後に行った後追い調査であり、本研究の方法設計には反映していない。

続編：Decision Modelは判断を控えられるか：7つのDecision Modelによるholdout-exp-2横断評価（同じholdoutで7つのDecision Modelを比較した技術版）

Abstract

長期的に関係を築くAIパートナーでは、文章生成とは別に、記憶を今使うべきか、候補を一意に選べるか、根拠が十分か、表出計画が場面に適しているか、といった多数の意味判断が必要になる。本研究では、この「判断層」を専用Decision Modelへ分離できるかを検討するため、TypeSafe AIのJev 1.13.0を4種類のContractで評価し、Gemini 3.1 Pro Preview、Gemini 3.8 Flash、GPT-6 Astra、GPT-6 Lunaと比較した。

Goldを生成系から隔離した260 logical cases（provider 256 + local deterministic 4）をone-shotで実行した。provider casesではJevが162/256で、Generic 4はいずれもこれを上回った。Generic 4平均との差は−0.085で、111 effective clustersを単位にしたpaired bootstrapでも95%区間[-0.131, -0.038]だった。ただし最も近いGemini Flashとのpairwise区間だけは0を跨いだ。

事後分析では、Jevには「根拠不足でも判断を確定する」「Partnerのcounterevidenceを取り違える」「Expressionを過剰に受容する」といった比較的頑健な弱点が確認された。一方、当初疑った「複数memoryを統合できない」という説明はblind qualitative reviewでは支持されず、feature単位の誤りの累積として解釈を修正した。評価途中ではPartner topic continuationとCBSの一部にruntime specification transferの問題も発見したが、該当範囲を全システムで対称的に扱う感度分析でもJevの相対差は消えず、むしろやや拡大した。

Jevのchoice-value separationを使った探索的cascadeでは、dev validation由来の中間policyで47.7%のcaseをJevが処理し、fallback-onlyに近いaccuracyを維持しながらAstra / Gemini Pro / Gemini Flashに対して31–39%のlist-price削減が得られた。しかしGPT-6 Lunaは単独でも今回のGeneric 4で最も高精度かつ極めて安価で、Jev→Luna cascadeはLuna-onlyより1.7%高くなった。

したがって現時点の実務的な結論は、専用Decision Modelを置くこと自体に価値があるわけではなく、安価で強い汎用LLMを直接judgeとして使う方が合理的な場合がある、というものである。一方で、より高価なfallbackを使う条件では、confidenceを持つfirst-pass decision layerに条件付きの価値が残った。

1. Introduction

1.1 AIパートナーを作ると、「生成」以外の判断が増えていく

筆者はこれまで、長期的な関係を持つローカルAI Partner Systemを開発してきた。

開発初期では、中心的な問題は比較的単純だった。ユーザーの入力と過去の会話をActorへ与え、キャラクターとして自然な文章を生成させればよい。

しかし記憶、proactive behavior、lifecycle、継続的な関係性を実装していくにつれ、発話生成の前後に多数の判断が必要になった。

例えばmemory retrievalでは、embedding上で似ている記憶を取得できることと、「その記憶を今この会話で使うべきか」は同じ問題ではない。

同じ対象についての記憶でも、現在とは反対の状態を記録した古い記憶かもしれない。意味的には強く関連していても、それを会話へ持ち出すとユーザーの現在の発言と矛盾する場合がある。

proactive behaviorでも同様だった。

「ユーザーが戻ってきたから声を掛ける」「しばらく同じ話題を続けているから続きを話す」「動画を見ている状態が続いている」といった振る舞いを実装しようとすると、hard-coded guardや例外条件が増えていく。

away/return、topic continuity、source attribution、activityの継続判定、重複proactiveの抑制などを個別にPythonで補正していけば、一つ一つの問題は解消できる。しかしシステム全体としては「意味判断をコードで再実装している」状態に近づいていった。

この経験から、次第に一つの疑問が強くなった。

生成モデルとは別に、「判断」を担当する層を置けないだろうか。

1.2 Irodori-TTSから、Expressionを独立した判断として考える

AIパートナーの重要な要素として、発話機構・TTSがある。

軽量な日本語TTSで、クオリティの高い感情表現が扱えるシステムとしてIrodori-TTSが存在する。Irodori-TTSでは、発話文に対応する絵文字を付与することで、音声の感情表現を制御できる。

ここで最初に考えたのは、

Actor自身に、発話本文と一緒に適切な絵文字まで生成させればよいのではないか

という単純な方法だった。

しかし、この方法ではActorに二つの責務を同時に持たせることになる。

  1. キャラクターとして自然な発話本文を生成すること
  2. TTS制御用の規則に従って、必要な感情表現を漏れなく付与すること

発話本文が自然でも、絵文字だけ抜けるかもしれない。逆に、会話としては自然でも、TTS側で許可していない形式や規則外の表現をActorが出す可能性もある。

そこで、

Actor
  ↓
発話本文
  ↓
Expression Judge
  ↓
感情・表出の判断
  ↓
対応する制御情報を後付け
  ↓
TTS / 表情 / 態度

という分離を考えた。

この発想はやがて、音声だけでなく、表情、視線、身振り、態度、delivery style、intensityなどを含む「Expression」全体を、semantic contentとは別のdecisionとして扱えないかという設計へ広がった。

本来の実装アイデアは「表出planを決める」ことだが、Jevは事前定義した選択肢に対して判断を返すモデルである。そこで本評価では、generation qualityと混同しないよう、

content、scene、recipientに対して、emotion・delivery intent・intensityからなる与えられたplanが適切か

を検証するContractへ落とした。

1.3 Character Behavioral Seed（CBS）で考えていたこと

別系統では、キャラクターそのものをどう表現・成長させ、ユーザーがAIパートナーを「知っていく」ということを実現できるかという問題を検討していた。

そこで考えたのが Character Behavioral Seed（CBS） である。

CBSの出発点は、

キャラクターを「優しい」「人見知り」「正義感が強い」といったtraitの一覧だけで定義するのではなく、
「このような状況では、この人はどのように反応しやすいか」という条件付きの反応傾向から人物を捉えられないか

という発想だった。

作者が人物の人生や全ての行動を事前に書き切るのでもなく、AIに全てを自由生成させるのでもない。複数のbehavioral probeやmicro-scenarioを「人物を観測するための点」として使い、条件付きで不完全な人物モデルを持たせる。

これにより、ユーザーが全てをpromptで設定するのではない、過去や嗜好などに構造的な未知の要素を持つ存在として、AIパートナーを「徐々に知っていく」ことを実現できるのではないかと考えた。

ここでも、対象候補の意味適合、CanonとOpenの境界、発話へ使ってよい根拠、生成結果と許可された人物情報の整合など、生成とは別の判断が必要になる。

1.4 4つの開発課題をContractへ切り出す

Partner System、Expression、CBSを並べると、共通して

候補を取得する → 意味的に評価する → 制約を適用する → Actorが表現する

という流れが見えていた。

もう一つ必要だったのが、Actorが発話や行動判断に使おうとしている命題が、現在許可されたevidenceから本当に支持されるかを確かめるgroundingである。これを Core.claim_support とした。

今回の4 Contractは、性質の違うclassification taskを恣意的に集めたものではなく、開発上の別々の判断問題をbounded decisionへ切り出したものである。

開発上の問題 Contract 評価したdecision
CBSで質問対象をgroundする CBS.target_fit 候補を一意に特定できるか、保留すべきか
Actorが使う主張をgroundする Core.claim_support claimがeligible evidenceで支持されるか
TTS・表情等の表出planを検証する Core.expression_fit 与えられたExpression planが場面に適合するか
取得したmemoryを今使えるか判断する Partner.memory_relevance relevance / counterevidence / continuationをどう判定するか

この「意味的に評価する」の部分を独立したDecision Layerとして扱えないか、という問題意識が本研究の出発点である。

1.5 用語

本稿では、似た言葉を次のように区別する。

  • System One Model: TypeSafe AIがJevなどに用いている製品・モデルカテゴリ名。
  • Decision Model: 本稿で使う一般カテゴリ。boundedな候補や判断を返す専用モデルを指す。
  • Jev: 今回評価したSystem One Model、version 1.13.0。
  • Jev R2: dev tuningで2回のinstruction revisionを経た、本研究用のfrozen adapter revision。
  • Decision Layer: 筆者側のarchitecture概念。Python hard rule、Decision Model、cheap LLM、strong fallbackなどを含み得る。
  • Contract: 入力、出力、意味規則、scoring boundaryを固定したdecision primitiveの仕様。
  • Generic 4: Gemini 3.1 Pro Preview、Gemini 3.8 Flash、GPT-6 Astra、GPT-6 Lunaの4システム。

1.6 Decision ModelとしてのJev

こうして「生成とは別に意味判断を担当する層を置けないか」という問題意識が複数の開発課題から収束し始めていた。

そのタイミングで、2026年9月15日、TypeSafe AIは最初のSystem One ModelとしてJevを公開した。

Jevは文章そのものを生成する用途ではなく、stateと事前定義されたquestionを受け取り、choiceやvalueを返すdecision primitiveとして提供される。この性質は、筆者がPartner System / CBS / Expressionで欲しかった中間層と近かった。

そこで、Jevと汎用LLMの双方へ同じ論理的Contractを解かせる比較を行った。

2. Methods

2.1 Research Questions

本研究では主に次の問いを扱った。

  1. Jev R2は、AIパートナーに関連するdecision taskで汎用LLMと比較してどの程度の性能を持つか。
  2. Jevはどの種類の判断で失敗するか。
  3. Jevのchoice-value separationは失敗検知に利用できるか。
  4. 観測された差は一部の特殊caseや難易度構成に依存するか。
  5. benchmark specificationの影響を取り除いても結論は維持されるか。
  6. standalone accuracyが低くても、Jevをfirst-pass decision layerとして利用する価値はあるか。

2.2 Contractと採点単位

Contract仕様

Contract 主出力 ラベル / 値 case-level exact match
CBS.target_fit status, selected_target resolved, no_match, ambiguous, insufficient_evidence statusとtargetの完全一致
Core.claim_support label, reason supported/entailed_in_scope, contradicted/explicit_conflict, undetermined/not_entailed, undetermined/insufficient_evidence label + reasonの完全一致
Core.expression_fit fit suitable, unsuitable, unclear, insufficient_evidence fitの完全一致
Partner.memory_relevance memoryごとの3 feature 各featureが yes, no, unclear, insufficient_evidence case内の全memory・全featureの完全一致

Expressionの assessed_features=[emotion, delivery_intent, intensity] はdeterministicに付与し、accuracyへ重複加点しない。Partnerの set_status もcandidate-set topologyからdeterministicに導出し、provider semantic scoreには含めない。

decision unit

case-level exact matchとは別に、abstention behaviorを調べるための最小判断単位を decision unit と呼ぶ。

  • CBS: 1 case = 1 decision unit
  • Claim: 1 case = 1 decision unit
  • Expression: 1 case = 1 decision unit
  • Partner: 1 memory × 3 features = 3 decision units

provider 256 cases全体では624 decision unitsになる。

yes/no、resolved/no_match、supported/contradicted、suitable/unsuitableのように判断を確定する側をdecisive、unclear / ambiguous / insufficient_evidence / undeterminedをabstention側として集計した。

  • false decisive: Goldがabstention側なのにpredictionがdecisive側
  • false abstain: Goldがdecisive側なのにpredictionがabstention側

ここでのabstention metricはdecision modeの診断であり、case exact accuracyとは別である。

Jev-only error

Jev-only error は、Jevが誤り、Generic 4が全て正解したcaseまたはdecision unitを指す。診断の文脈ごとにcase / unitのどちらかを明記する。

separation / margin

Jevは各choiceにvalueを返す。本研究ではそれらをcalibrated probabilityとは呼ばず、

margin = top1 value − top2 value

をchoice separationの記述量として使用した。

説明用の架空例

以下はContractの意味を説明するために作った説明用の架空例であり、holdout caseそのものではない。

CBS.target_fit

Question: 「昨日、風車を直した係は？」
Candidates:
- c1: 昨日、風車を修理した整備係
- c2: 昨日、風車の絵を描いた記録係

Gold:
status = resolved
selected_target = c1

Core.claim_support

Claim: 「Aは作業を完了した」
Evidence: 「Aは明日その作業をする予定だと話した」

Gold:
label = undetermined
reason = not_entailed

proposal / intentionはexecutionをentailしないためである。

Core.expression_fit

Content: 「結果を説明します」
Plan: neutral / explain / moderate
Scene: neutralな説明。lowまたはmoderateが適切

Gold:
fit = suitable

Partner.memory_relevance

Current: 「電球はもう交換した」
Memory: 「電球が壊れている」

Gold（概念例）:
relevant_now = yes
counterevidence = yes
topic_continuation = no

同じ対象でも現在stateと異なるmemoryは、semantic similarityだけでは扱えないことを示す例である。

split

split provider local 用途

holdout-exp-2の作成

holdout-exp-2は AI-assisted clean-room synthetic benchmark である。

provider 256 casesのsemantic authoringとinitial provisional Goldは、評価対象5systemとは別のClaude Opus 5.5 sessionで作成した。authorはfrozen specification、coverage plan、authoring guideを参照したが、evaluated-system output、benchmark score、過去holdoutにはアクセスしない手順とした。

Claude系は今回のevaluated five systemsに含まれていない。そのため「Gold authorと同じmodel familyが比較対象の一つだけに直接有利に働く」という形のbiasは避けられている。一方で、Gold自体はAI judgmentを含むため、絶対accuracyの解釈ではauthoring / interpretation noiseの可能性を残す。

first-pass blind reviewでは、provider 256件のうちsemantic judgmentが得られた255件中226件がauthor provisional Goldとexact agreement、29件がdisagreementだった（agreement 88.6%）。1件はoperational no-judgmentだった。最終freezeではprovider 256件のうち227件がprovisional layer、27件がadjudication後のlayer、2件がrepair後のlayerをcurrent Goldとしてbindingした。これは29件すべてでauthor provisional Goldが変更されたことを意味しないが、29件がsemantic adjudicationを必要としたことを示す。

その後、review / adjudication / consistency / independence auditを経てGoldをfreezeした。これは人手のみで作成したdatasetではなく、review independenceも完全なmulti-human independenceではない。隔離は主としてprocessとcustodyによるものであり、この点はLimitationsとして扱う。

provider casesは4 Contractそれぞれ64件。Partner provider 64 casesには合計144 memoriesがある。112 authoring families、111 effective clustersを持ち、既知のdependency 1件のみ2 familiesを1 clusterとして扱う。

local deterministic 4 cases

local 4 casesは、Partnerの memories=[] を扱うContract completeness用caseである。

この場合、semantic questionをproviderへ送る必要がなく、

assessments = {}
set_status = insufficient_evidence

をdeterministic ruleで返す。

全システムで同じ結果になるため、モデル比較の主な分析はprovider /256を中心に行い、/260はsystem-level completeness指標として併記する。

2.4 Evaluated systemsとadapter

formal holdoutでは、全システムについて 1 provider case = 1 fresh provider request とした。Partnerに複数memory・複数featuresがある場合も、Jevをfeature数だけ別API callしたわけではなく、1 case requestの中に複数のtyped decision questionsを含める。

provider cases 256 × 5 systems = 1280 physical sendsである。local casesはprovider callを行わない。

System exact model ID adapter / surface 主な設定
Gemini 3.1 Pro Preview gemini-3.1-pro-preview generateContent / shared generic prompt JSON schema, candidateCount=1, includeThoughts=false, timeout 60s
Gemini 3.8 Flash gemini-3.8-flash generateContent / shared generic prompt JSON schema, candidateCount=1, includeThoughts=false, timeout 120s
GPT-6 Astra gpt-6-astra Responses API / shared generic prompt reasoning effort=medium, strict JSON schema, tools=[], store=false, timeout 120s
GPT-6 Luna gpt-6-luna Responses API / shared generic prompt reasoning effort=medium, strict JSON schema, tools=[], store=false, timeout 120s
Jev jev-1.13.0 SystemOne SDK 0.7.0 / R2 decision guidance finite choice questions, timeout 30s

temperature / top_p / provider sampling seed / service tierは全systemでrequestに明示指定しなかった。case-order seedはsampling seedではない。

formal holdout runは2026-10-01 00:33 JSTごろにexecution manifest / authorizationをfreezeし、その後one-shot generationを実施、同日02:04 JSTごろに全5systemのgeneration sealを作成した。concurrency=1、automatic retry=0、fallback=0である。

1280 provider callsはすべてPARSED_SUCCESSで完了し、systemごとのoperational / parse / timeout / transport failureは0だった。したがって、運用失敗によって除外されたcaseや、運用失敗をsemantic errorとして数えたcaseはない。

timeoutはJev 30s、Gemini 3.1 Pro Preview 60s、その他120sとsystemごとに異なる。これはprovider / adapterごとにfreezeしたoperational ceilingであり、cross-providerの計算量を等しくするための条件ではない。本runではtimeoutが1件も発生していないため、primary scoreに欠測を生じさせてはいない。

instruction parityとJev tuning

この比較は、instruction wordingの完全な対称性を目指したものではない。

Generic 4は共通の generic_prompt を使ったoff-the-shelf zero-shot baselineであり、provider別prompt tuningは行っていない。

一方Jevは本研究のspecialized targetとして、dev tuning splitのみを使った最大2 revisionを事前に許可した。Generic 4のsemantic結果を見る前にJev final configをfreezeした。

Jev tuning上のcase exactは、

  • baseline: 39/50
  • R1: 46/50
  • R2: 47/50

だった。

R1では、複数familyに共通したfailure patternに基づいて、

  • missing evidenceとnegative evidence
  • Partner feature間の独立性
  • entailmentとcontradiction
  • conditional Expression suitability

の一般instructionを明確化した。

R2ではCBSのevidence completenessとreferential ambiguityの区別のみを追加調整した。case ID固有patch、Gold answerの埋め込み、Generic model answerの参照は行っていない。

最終的にR2をfreezeしてholdoutへ使用した。

後のspecification auditでは、Partner topic continuationに関するJev R2の追加guidanceの一部が、Gold authoring側のfrozen ruleと非等価で、state-change caseでは逆方向を指すことが判明した。これはJev model capabilityそのものとは分離して扱い、感度分析を行った。

2.6 Primary metricとanalysis hierarchy

Gold access前に固定したprimary semantic metricは Contract-level exact semantic match である。

  • CBS: status + selected_target
  • Claim: label + reason
  • Expression: fit
  • Partner: case内の全memory・全feature

をContract仕様どおり完全一致で採点した。

overall provider accuracy /256は、4 Contractsをまとめたaggregate summaryとして報告する。weighted composite scoreは作らなかった。

研究全体をpreregisterしたわけではない。区別は次の通りである。

  1. Primary benchmark
    generationをGold access前にsealし、scorer / metric definitionもGold access前にfreezeした。
  2. Post-hoc quantitative diagnostics
    error overlap、margin、cluster bootstrap、difficulty、historical comparison。
  3. Post-hoc blind qualitative diagnostics
    機械的に選んだdiagnostic sampleをfresh reviewerがsystem identityを伏せて評価。
  4. Specification audit / sensitivity analysis
    Gold authoring ruleとruntime-visible semanticsを別々に監査し、影響範囲を全systemで対称処理。
  5. Deployment simulation
    dev由来thresholdで既存predictionをcase-level routingし直した探索的cascade。

post-hoc analysesでは可能な範囲で、outcome-conditioned joinやunblindingの前にその分析内のmethodをfreezeしたが、primary benchmarkと同じ意味での事前登録ではない。

Flashとの全体差が最も小さい背景にはContract構成もある。ClaimではJev 48/64に対してFlash 40/64とJevが8件上回る一方、CBS（48 vs 55）、Expression（45 vs 52）、Partner provider（21 vs 29）ではFlashがJevを上回った。したがって、Flashとのintervalが0を跨ぐことを「全Contractでほぼ同等」とは解釈しない。

3.2 Cluster-aware robustness

111 effective clustersを単位に50,000回のpaired cluster bootstrapを行った。

1 clusterずつ除外してもJev − Generic 4平均は−0.094〜−0.080の範囲に収まり、family macro / cluster macroでもほぼ同じ差だった。

また、Jev-only case errors 21件は21個の異なるclusterへ1件ずつ分散していた。

したがって、Jevの相対的な不足を少数の特殊clusterだけで説明することは難しい。

3.4 頑健だったfailure mode

False decisiveness

624 provider decision unitsで、Jevのfalse decisiveは57だった。Generic 4は12〜30。

dev validationでも同方向の差があり、材料不足やambiguousな場面でdecisionを確定し過ぎる傾向はpersistentだった。

Counterevidence

Partner counterevidenceはJev 115/144に対しGeneric 4は137〜142/144。

blind diagnostic reviewでは、COUNTEREVIDENCE_POLARITY と分類された3 outputsがunblind後すべてJevだった。また「矛盾・反証的memory injection」に分類されたoutputはJev 7、Generic 4は各0だった。

Expression overacceptance

diagnostic sampleで選ばれたJev Expression errors 8件のうち7件は、unsuitable / unclearをsuitable側へ寄せるoveracceptanceだった。

AIパートナー上の意味

Failure mode システム上で起こり得ること
false decisiveness 本来「分からない」とすべきmemoryやtargetを確定して扱う
counterevidence polarity 現在のユーザー発言と矛盾するmemoryを、支持材料のように扱う
Expression overacceptance 場面・相手に合わない声色や態度のplanを通す
feature uncertainty placement 不明なのは一部featureだけなのに、別featureを確定／保留してしまう

この表はUX consequenceの説明であり、blind sampleからfailure prevalenceを推定するものではない。

3.5 当初の仮説が崩れた点

Partnerのcase-level exactが低かったため、途中では「複数memoryを統合する能力」の不足を疑った。

しかしpost-hoc diagnostic reviewでは、freshなClaude Opus 5.5（effort High） reviewerがsystem identityを伏せた30 diagnostic cases / 150 outputsをblind reviewした。その結果、CROSS_MEMORY_INTEGRATION がprimary mechanismになったcaseは0だった。

むしろ、

  • counterevidence
  • ambiguityがどのfeatureにかかるか
  • topic continuation

といったfeature-level errorが複数重なり、case exactを失っていると解釈する方が適切だった。

したがって「memoryは複数featureに分けるべき」という点はbenchmark designの前提であり、結果から新たに得た知見は、実際のcase failureも一つの“memory integration能力”よりfeature-level errorsの累積として説明しやすかったことである。

3.6 Benchmark specification audit

blind reviewの過程で、benchmark側にも仕様問題が見つかった。

Partner topic continuationでは、Gold authoring側に

same object AND same state

が必要というruleがGold作成前からfreezeされていた。しかしGeneric 4へ渡されたruntime wordingは曖昧な same object/state だった。

さらにJev R2には、state-change caseでauthoring ruleと逆方向に読める追加guidanceが存在した。

CBSでも、retrieval_state=not_retrievedならcandidate universeの完全性を確立できないためinsufficient_evidenceとするauthoring ruleがruntimeへ伝達されていなかった。

これはJev model capabilityではなく、benchmark / adapter specification transferの問題として扱った。

公式scoreは変更せず、

  • CBSのaffected 4 cases
  • Partnerのfrozen different_state 26 topic units

を全systemで対称的に扱うsensitivity analysisを行った。

3.7 Cascade simulation

Jevのmarginとerrorにはdev validationから持続する関係があった。holdoutの624 decision unitsでは、正解unitのmargin中央値が0.88、誤りunitの中央値が0.39（誤り158 units）で、Cliff's δ（誤り vs 正解）は−0.54だった。dev validationでも正解0.83、誤り0.28（13 units）、δ=−0.62で、方向は一貫していた。false-decisive vs correct-decisiveに限ったholdoutのδも−0.56だった。

そこで、

Jevをfirst-passで使い、case内の最小marginがthreshold未満ならGeneric modelへcase全体をfallbackする

cascadeを探索的にsimulationした。

policyの意味

thresholdはholdoutで最適化せず、dev validationからContract別にfreezeした。

  • ACCEPT_75: dev case confidenceの25 percentile
  • ACCEPT_50: dev median
  • ACCEPT_25: dev 75 percentile

名前は「devでおおむね何割を受理する位置か」を表す。holdoutで同じcoverageになるよう再調整していない。

holdoutでの実際のoverall Jev coverageは、

Policy Holdout coverage
ACCEPT_75 79.7%
ACCEPT_50 47.7%
ACCEPT_25 24.2%

だった。

4. Discussion

4.1 現時点の実務的な答え：まずcheap generic LLMが強い

今回のデータから最も直接的に言えるのは、現行Jev R2をstandalone judgeとして採用する根拠はなく、今回比較した条件ではGPT-6 Lunaのような安価で強い汎用LLMを直接judgeとして使う方が合理的だった、ということである。

LunaはGeneric 4の中でprovider accuracyが最高で、benchmark list priceも桁違いに安かった。Jev→Luna cascadeはLuna-onlyより1.7%高く、accuracyもLuna-onlyを上回らなかった。

したがって、現在のJevについては、

  • standalone: どのContractでも支持しない
  • cascade candidate: Claim、Expression、仕様修正後のCBS
  • Partner: current R2ではnot ready

と整理する。

ただしExpressionはACCEPT_50 coverageが15/64（23%）しかなく、受理したcaseでfallback-correctを損ねた数は0だったものの、ほとんどのcaseをfallbackへ送るため経済的な削減余地は小さい。Expressionをcascade candidateと呼ぶのは、主にerror routingが機能したという意味であり、大きなcost savingを示したという意味ではない。

Partnerをnot readyとする理由は、単なるaccuracyの低さだけではない。counterevidence polarity、false decisiveness、矛盾memory injectionの一部が高confidenceで残ること、加えてR2 runtime wordingにspecification mismatchがあったためである。

4.2 専用Decision Modelを置く意味はどんな条件で生まれるか

Jevではchoice-value marginがerrorと持続的に関連し、実際に複数のerror typeをfallbackへroutingできた。

しかし、ここから

専用Decision Modelだからgeneric LLMより良いconfidenceが得られる

とは言えない。

本研究では、Generic 4から取得可能なlogprob相当のsignal、self-consistency、secondary judgeなどを使ったconfidence routing baselineを比較していない。

したがって示せたのは、

Jevのdecision valueには、少なくとも本データ上でroutingに使えるsignalが存在した

までである。

専用Decision Modelの経済的価値が生まれる条件は、

Decision Model自身のcost + 残ったfallback cost < generic modelを直接使うcost

であり、同時にquality / failure riskが許容範囲へ収まることである。

Astra / Gemini Pro / Gemini Flashをfallbackにした探索的simulationではこの条件が一部成立した。しかしLunaでは成立しなかった。

したがって「Decision Modelは有望」と一般化するより、

より高価なfallbackを使う環境では、安価でconfidenceを返すfirst-pass decision layerに条件付きの価値があり得る

と読む方がデータに忠実である。

4.3 AIパートナーにとってMemoryは一つの判断ではない

benchmarkを設計した時点から、memory relevanceを一つのscoreに潰さず、

  • semantic relevance
  • current-state consistency
  • counterevidence
  • uncertainty
  • topic-continuation value

のような異なるdecisionへ分ける必要があると考えていた。

結果から新しく分かったのは、Partnerのcase-level failureも「一つのmemory integration能力」で説明するより、これらfeature-level errorが積み重なったものとして説明しやすかったことである。

semantic similarityの高いmemoryが、今使うべきmemoryとは限らない。

「昨日、電球が壊れていた」というmemoryと「今日、その電球は交換済みである」というcurrent stateは対象として極めて近い。しかし、retrieval similarityと「会話へ出してよいか」は別問題である。

今後のarchitectureでは、

  1. embedding / indexでcandidateを取得
  2. semantic judgeで現在性・反証・不確実性を評価
  3. deterministic policyで権限・TTL等を適用
  4. Actorへ渡す

という責務分離の方が自然に見える。

4.4 Python、Decision Layer、Actorの責務を分ける

今回の経験から、将来的にはPythonで意味判断を作り込む範囲を狭めたい。

Pythonに残すべきなのは、

  • TTL
  • state machine
  • deduplication
  • lifecycle
  • permissions
  • transaction
  • deterministic constraints

のようなhard ruleである。

一方、

  • このmemoryを今使うべきか
  • 現在の発言と矛盾するか
  • どのfeatureだけがuncertainか
  • Expression planは適切か

といったsoft semantic judgmentは、まずcheap general-purpose LLMを有力候補として考え、その価格性能やprivacy要件次第でspecialized Decision Modelやstrong fallbackを組み合わせる方が、今回のデータには合っている。

将来的にCBSとPartner Systemを統合するなら、

Orchestrator
  ├─ Deterministic Layer
  ├─ Retrieval Layer
  └─ Semantic Decision Layer
          ├─ cheap LLM
          ├─ specialized Decision Model
          └─ stronger fallback
                ↓
              Actor

という分離も考えられる。

Actorは「キャラクターそのもの」ではなく、状態・intent・evidenceを受けてキャラクターとして表出する担当へ寄せる。

privacy / offline性

本研究では評価していないが、AIパートナーではcostやaccuracy以外にprivacy / offline availabilityも重要である。

長期memoryやrelationship stateをクラウドjudgeへ送ること自体が設計上のtrade-offになる。したがって、多少accuracyが低くてもローカル小型モデルやlocal Decision Layerを選ぶ合理性はあり得る。

今回のbenchmarkはこの軸を測っていないため、deployment decisionでは別途評価が必要である。

4.5 Jevをさらにtuneするべきか

今回見えたfailure modeは一様ではない。

  • false decisiveness / low-margin ambiguity: calibration / routing候補
  • counterevidence polarity: targeted instruction / tuning候補
  • Expression overacceptance: boundary clarification / routing候補
  • high-confidence residual semantic errors: 単純thresholdでは解決しにくい

したがって「Jevをさらに調整すれば解決する」とも、「次モデルを待つしかない」ともまだ言えない。

ただし現時点では、Jevを追加調整して既存cheap generic LLMへ追いつかせること自体がdeployment上の目的になるのか、という経済的問いも同時に考える必要がある。

4.6 別のDecision Modelが出たとき、初めて分かること

本研究で評価したspecialized Decision ModelはJevだけである。

したがって今回確認した弱点が、

  • Jev固有
  • specialized Decision Model一般
  • 問題そのものがLLM全般に難しい

のどれなのかは分離できていない。

特に有用な将来比較は、

  1. raw cheap general-purpose model
  2. 同じ、あるいは近いbase familyをDecision用途に特化したAPI / model
  3. Jev
  4. strong generic fallback

である。

さらにroutingを比較するなら、

  • Jev confidence → fallback
  • cheap generic LLM confidence → fallback

の両方を同じ未使用holdoutでprospectiveに比較する必要がある。

6. Limitations

本研究には複数の制約がある。

  1. specialized Decision ModelはJev一つしか評価していない。
  2. holdoutはprovider 256 casesと小規模である。構造dependencyは111 effective clustersで扱った。
  3. datasetはAI-assisted synthetic benchmarkであり、人間だけで作成した自然会話corpusではない。
  4. author / reviewerの独立性はcustodyとprocessによるもので、完全なmulti-human / model-family independenceではない。
  5. Jevだけはdev tuningでinstruction revisionを許可し、Generic 4はshared zero-shot promptであるため、instruction parityは完全ではない。
  6. 後のauditでJev Partner instructionの一部がGold authoring semanticsと非等価であることが判明した。
  7. CBS not_retrievedにもruntime specification transfer gapがあった。
  8. これら仕様問題は感度分析しても主なsystem gapを消さなかったが、affected taskの能力解釈は慎重に行う必要がある。
  9. error analysis、blind qualitative review、cascade simulationはpost-hoc exploratoryである。
  10. blind qualitative sampleはfailure-richに選定しており、failure prevalenceを推定できない。
  11. dev setsは小さく、tuning splitは独立testではない。
  12. Partnerのdev dataは1 case 1 memoryで、holdoutと構造が異なる。
  13. cascadeは既存predictionをofflineでroutingし直したsimulationであり、本番serial executionではない。
  14. costはbenchmark list priceによる計算で、実請求額そのものではない。
  15. latencyはobserved-callを足したproxyしかなく、production cascade latencyは測っていない。
  16. Jev marginをgeneric LLM由来のconfidence signalと比較していない。Jev固有のconfidence advantageは示していない。
  17. privacy / offline性はdeployment上重要だが、本benchmarkでは測っていない。
  18. 修正版Partner R2は実行していない。
  19. full holdout / Goldは将来のDecision Model比較に再利用できるよう、現時点では公開前提にしていない。公開する場合は将来評価へのcontaminationを考慮する必要がある。

RQ4. 差は少数caseや難易度依存か 111 clustersを考慮しても差は残り、Jev-only case errorsも21 clustersへ分散した。
RQ5. specification問題を除いても結論は残るか 残る。対称sensitivityではGeneric平均との差は−0.085から−0.102 / −0.103へむしろ拡大した。
RQ6. first-pass Decision Modelとして価値はあるか 高価なfallbackでは条件付き価値が見えた。Lunaほど安く強いfallbackでは経済的価値はなかった。

8. Conclusion

Jev 1.13.0 / R2を、AIパートナーおよびキャラクター実行系に関連する4種類のdecision taskで評価した。

公式holdoutではJevはprovider 162/256で、Generic 4のpoint estimateを全て下回った。cluster-aware analysis、historical comparison、blind qualitative review、specification auditを経ても、相対的な不足は消えなかった。

頑健だったfailure modeは、

  • evidence不足で判断を確定しすぎる
  • Partnerでcounterevidenceを取り違える
  • Expressionを過剰にacceptする

ことである。

したがって、現行Jev R2をstandalone judgeとして展開することは支持しない。

一方、Jevのmarginにはrouting signalがあり、高価なfallbackを使う条件では、Jevをfirst-passに置く探索的cascadeがqualityを大きく損なわずcostを下げるケースがあった。

しかし今回、GPT-6 LunaはGeneric 4の中で最も高いaccuracyと非常に低いcostを同時に示した。Jev→Luna cascadeはLuna-onlyより高くなり、qualityでも優位を示さなかった。

したがって本研究から得られる最も実務的な結論は、

現時点では、十分に安く強い汎用LLMがあるなら、それを直接semantic judgeとして使う方が合理的である。

その上で、

専用Decision Modelは、generic model単独より良いcost / quality / calibration trade-offを提供できる場合にのみ、first-pass判断層として価値を持つ。

という条件付きの可能性が残る。

またAIパートナーのmemory systemについては、「記憶を検索できるか」より後段に、その記憶を今使うべきかという独立したdecision problemが存在する。

今回の評価は、今後Partner SystemとCBSをOrchestrator中心のarchitectureへ再構成し、

  • deterministic code
  • retrieval
  • semantic judgment
  • Actor generation

を分離していくための一つの設計材料になった。

次に必要なのは、仕様を修正したbenchmark versionで、

  • cheap generic LLM judge
  • future specialized Decision Model
  • confidence-based routing

を同じ未使用holdoutでprospectiveに比較することである。
